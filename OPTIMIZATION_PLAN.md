# План оптимизации SmartVolumeMixer (бриф для Opus 5.5)

Составлен 2026-11-16 по чтению `src/` и замерам живого процесса. Перед началом прочитай `CLAUDE.md` целиком: там модель потоков, COM-апартаменты и инварианты, которые этот план не повторяет, но которые нельзя нарушать.

## 1. Цель и главный вывод

Цель: приложение должно быстрее реагировать и потреблять меньше ресурсов, без изменения поведения.

Главный вывод из замеров: **в покое оптимизировать почти нечего**. Прошлые проходы уже сделали основное (см. раздел 10). За 347 минут работы процесс потратил около 0,7 с CPU и держит 3,7 МБ приватной памяти. Поэтому не трать время на "снижение CPU в простое": выигрыш будет в пределах шума.

Реальный остаток лежит в четырёх местах, по убыванию пользы:

1. **Задержка первого OSD после простоя.** Через 30 с простоя D3D-устройство освобождается, и первое же движение ролика платит за его пересоздание (по комментарию в коде ~45 мс) плюс холодную WASAPI-цепочку плюс один скрытый кадр ImGui. Это единственное место, где пользователь может заметить медлительность.
2. **Стоимость кадра, пока OSD на экране.** Каждый `Present` копирует полноэкранный буфер в layered-окно с color key. Во время прокрутки ролика это идёт почти непрерывно и может стоить кадрового времени игре.
3. **Старт и пик памяти.** При запуске создаётся D3D-устройство и шрифтовой атлас, которые через 30 с выбрасываются. Пик рабочего набора 40,5 МБ при 13,9 МБ в покое.
4. **Что загружено в процесс.** Несколько DLL грузятся при старте, хотя нужны только редким функциям.

## 2. Исходная точка

Замерено на бинарнике от 2026-11-01 (исходники не новее него), PID работал 347 минут, оверлей скрыт.

| Метрика | Значение |
|---|---|
| CPU всего | ~0,7 с (поток хука ~0,48 с, UI ~0,20 с, worker ~0) |
| Потоки | 3 |
| Хэндлы | 221 |
| Private bytes | 3,7 МБ |
| Working set / пик | 13,9 МБ / 40,5 МБ |
| Загружено модулей | 48 |
| GPU-память в покое | 0 МБ dedicated, 0 МБ shared |
| Размер exe | 907 КБ (`.text` 648 КБ, `.rdata` 139 КБ, `.rsrc` 81 КБ) |

Оговорка: время потоков Windows считает по тикам таймера, короткие всплески недоучитываются. Для сравнений "до/после" используй `QueryProcessCycleTime` / `QueryThreadCycleTime`.

Бюджеты, которые нельзя ухудшить: 3 потока в покое, private bytes, 0 МБ GPU в покое, отсутствие новых периодических пробуждений.

## 3. Правила работы

- **Живой экземпляр запущен из `build/Release/` и это рабочий инструмент пользователя.** Пока он остановлен, клавиша Mute глушит всю систему. Собирай в отдельный каталог (`cmake -B build-opt -S .`), чтобы рабочий бинарник оставался запасным. Перед остановкой живого экземпляра предупреди пользователя, после тестов запусти его обратно.
- Два экземпляра одновременно дают два хука и двойные шаги громкости. Тестируй только один.
- `config.json` лежит рядом с exe. Для тестового бинарника скопируй рабочий конфиг, иначе получишь дефолты.
- **Не нажимай `Alt+S` и `Alt+Q` в тестах сам**: они переключают вход монитора, основной дисплей и частоту ЦАП на реальной машине. Если шаг требует такой проверки, попроси пользователя.
- OSD появляется только когда играет приложение из whitelist. Для сценариев с роликом нужен запущенный плеер (например Spotify); уточни у пользователя, что запущено.
- Каждое изменение: замер до, замер после, одно изменение на коммит. Не дало измеримого эффекта, значит откати, а не оставляй "на всякий случай".
- Рабочее дерево сейчас целиком не закоммичено (ветка `main`). До начала спроси пользователя, сделать ли базовый коммит на отдельной ветке, иначе диффы оптимизаций будет не отделить. Сам не коммить без разрешения.
- Инварианты из `CLAUDE.md` §5 действуют все. Особенно: хук остаётся установленным (#1), сбой worker не выходит наружу (#2), SEH-обёртки без C++-локалов с деструкторами (#7), `RequestRedraw()` на любое изменение экрана (#10), только `RebuildFonts` строит атлас (#11), узкие строковые литералы только ASCII (#12).
- Если меняешь поведение, описанное в `CLAUDE.md` или `ARCHITECTURE.md`, обнови их в том же коммите.

## 4. Этап 0. Измерительная обвязка (обязателен, делается первым)

Без него остальные этапы превращаются в угадывание. Ни один следующий этап не начинай, пока нет базовой таблицы.

**Встроенные таймеры.** CMake-опция `SVM_PERF` (по умолчанию OFF) и заголовок `src/Perf.h` со scoped-таймером на `QueryPerformanceCounter`, пишущим строки в `perf.log` рядом с exe. При OFF макросы раскрываются в пустоту. В самой `LowLevelKeyboardProc` ничего не пиши и не блокируй: только счётчик вызовов и сумма циклов в атомиках, сброс при выходе.

Точки замера:

- Старт: `Config.Load`, `AudioManager::Initialize`, `OverlayWindow::Create` с разбивкой на `D3D11CreateDevice`, инициализацию ImGui, `RebuildFonts` (отдельно `FindFontPath`, построение атласа, `ImGui_ImplDX11_CreateDeviceObjects`).
- `RecreateDevice` с той же разбивкой, `CreateSwapChain`.
- `RenderFrame`: `NewFrame`, `UIManager::Render`, `RenderDrawData`, `Present`.
- Worker: `GetSessionEnumerator` холодный и тёплый, `ChangeVolume` целиком, `TogglePlayPause`, `GetCurrentTrackInfo`.
- Сквозная: от извлечения тика из очереди до возврата `Present` кадра, на котором OSD реально виден.

**Внешние скрипты** в `tools/perf/` (PowerShell): снимок процесса (private, WS, пик, хэндлы, потоки, число модулей, cycle time, счётчики `\GPU Process Memory`) и инжектор ввода через `SendInput` (серии `VK_VOLUME_UP/DOWN`, клавиша track info). Инжектированные клавиши хук обрабатывает как настоящие.

**Сценарии:**

| # | Сценарий | Что фиксировать |
|---|---|---|
| S1 | Холодный старт, затем 60 с покоя | время старта по фазам, пик WS, снимок в покое |
| S2 | Серия тиков после 35+ с простоя | сквозная задержка до видимого OSD, её разбивка |

Результаты заноси в таблицу в конце этого файла (раздел 11). Каждый сценарий прогоняй минимум 5 раз, записывай медиану и разброс.

## 5. Этап 1. Задержка появления OSD

Приоритет по порядку пунктов. После каждого повторяй S2 и S4.

**1.1. Первые два кадра без паузы.** ImGui раскладывает авторазмерное окно скрытым на кадре появления, поэтому OSD виден только со второго кадра, а между кадрами выдерживается `kFrameIntervalMs = 16` (`src/OverlayWindow.cpp:93`, логика в `RunLoop` около строк 448-455). Когда в маске появился новый бит, рисуй первые два кадра подряд. Комментарий над `kFrameIntervalMs` устарел: он ссылается на то, что хук живёт в этом потоке, а это давно не так. Ожидаемо: минус ~16 мс на каждое появление любого попапа, не только после простоя.

**1.2. Прогрев устройства параллельно с аудио-работой.** Сейчас render-поток узнаёт о необходимости устройства только после того, как worker закончил `ChangeVolume` и вызвал `ShowOSD`. Добавь `OverlayWindow::RequestPrewarm()`: worker вызывает его в начале обработки событий, способных показать попап (типы 0, 3, 4, 5, 6, 8, 9), render-поток при отсутствии устройства сразу делает `RecreateDevice()`. При пороге debounce 2 первый тик OSD не показывает, так что устройство успеет подняться, пока worker ждёт второго.
- Признак "устройство есть" сейчас живёт только в render-потоке (`m_deviceObjectsReady`). Для проверки из worker нужен атомарный дубль, чтобы не слать сообщение на каждый тик.
- После прогрева без показа обязательно взведи `m_idleCleanupAt`, иначе случайный одиночный тик оставит устройство жить навсегда и сломает бюджет "0 МБ GPU в покое".
- Вызывай из worker, а не из `LowLevelKeyboardProc`.

**1.3. Удешевить шрифтовой атлас.** Он растеризуется заново при каждом выходе из простоя: два кегля, полный диапазон `GetGlyphRangesCyrillic()`, `ImFontConfig` по умолчанию (`src/OverlayWindow.cpp:63,70,214`, в ImGui 1.90.4 это `OversampleH = 2`). Сначала по данным этапа 0 выясни, какую долю `RecreateDevice` занимает атлас. Если заметную, пробуй по очереди:
- `OversampleH = 1` вместе с `PixelSnapH = true`: вдвое меньше пикселей по ширине. Это меняет вид текста, поэтому сделай скриншоты до/после и покажи пользователю, решение за ним.
- `ImFontAtlasFlags_NoPowerOfTwoHeight`: меньше текстура без изменения вида.
- Свой статический диапазон без Cyrillic Extended-A/B и Supplement. Эффект может быть малым, если в шрифте этих глифов и так нет.
Фиксируй время построения, размер текстуры и пик WS.

**1.4. Холодная WASAPI-цепочка.** `kChainTtlMs = 1500` (`src/AudioManager.cpp:43`) означает, что первый тик после паузы всегда платит за три RPC и за `OpenProcess` по каждой сессии, потому что кэш имён чистится вместе с цепочкой. Только замерь. Менять стоит, лишь если холодный путь окажется дольше ~5 мс. Тогда вариант: инвалидация по `IMMNotificationClient::OnDefaultDeviceChanged` вместо TTL. Учти, что это может добавить поток в покое, а это нарушение бюджета, которое должно окупиться цифрами.

Критерий этапа: медиана S2 снизилась, S6 и снимок покоя не ухудшились.

## 6. Этап 2. Старт и пик памяти

**2.1. Не создавать D3D-устройство при запуске.** `OverlayWindow::Create` вызывает `CreateDeviceD3D`, `ImGui_ImplDX11_Init` и `RebuildFonts` (`src/OverlayWindow.cpp:139,158,163`), а через 30 с `IdleCleanup` всё это освобождает. Путь "устройства нет" уже есть: `RenderFrame` → `RecreateDevice`. Оставь в `Create` окно, контекст ImGui, Win32-бэкенд и трей, а устройство пусть появляется по первому кадру.
- Побочный плюс для инварианта #1: сейчас сбой `CreateDeviceD3D` на старте завершает приложение вместе с хуком, а после изменения хук останется жив.
- Проверь, что ничто не обращается к `ui.fontNormal` / `fontLarge` до первого кадра.
- Резолв пути шрифта (скан реестра в `FindFontPath`) можно оставить на старте, чтобы не переносить его в задержку первого OSD.
- Стартовую очистку (`HeapCompact` и trim рабочего набора) сохрани, задержку для неё можно сократить.
- Проверь путь аварийного перезапуска: он должен стать быстрее, а не сломаться.

**2.2. Delay-load для `d3d11.dll`** (только после 2.1). Статический импорт подтверждён `dumpbin`. Тогда сессия без единого OSD не загрузит `d3d11`, `dxgi`, `dxcore`, `directxdatabasehelper`. Не выгружай DLL обратно через `FreeLibrary`: риск большой, выигрыш нулевой.

Критерий: пик WS в S1 заметно ниже 40 МБ, время до установки хука не выросло, S2 не ухудшился.

## 7. Этап 3. Что загружено в процесс

Все пункты дешёвые и независимые. Эффект каждого малый, проверяется списком модулей и private bytes.

**3.1. Иконка.** `src/ico2.ico` содержит один кадр 256x256 в PNG (80,7 КБ), а `LoadImage` запрашивает 16 и 32 пикселя (`src/OverlayWindow.cpp:122-124,171`). В процессе висят `WindowsCodecs.dll` (2,3 МБ) и `IconCodecService.dll`; вероятная причина в декодировании PNG-иконки. Собери ICO с BMP-кадрами 16/20/24/32/48 и опциональным PNG 256. Проверка: оба модуля пропали из списка, иконка в трее выглядит не хуже.

**3.2. Delay-load редких DLL.** Статически импортируются `SETUPAPI.dll` (только `src/AmdDdcSideChannel.cpp:19-40`), `dxva2.dll` (только DDC/CI) и `dwmapi.dll`. Все три нужны лишь быстрым действиям. Добавь `/DELAYLOAD:` и `delayimp` в `CMakeLists.txt`.
- Проверка без переключения монитора: кнопка "Rescan monitors" в меню проходит через `dxva2` в режиме чтения.
- Путь `SETUPAPI` достижим только в AMD-фолбэке при реальном `Alt+S`. Попроси пользователя сделать один круг PC→консоль→PC в конце этапа.

**3.3. `imgui.ini`.** `io.IniFilename` нигде не задан, поэтому ImGui пишет `imgui.ini` в текущий каталог процесса. В репозитории уже три таких файла (корень, `build/`, `build/Release/`). Задай абсолютный путь рядом с exe, чтобы сохранить запоминание позиции меню, либо `nullptr`, если пользователь от него откажется.

**3.4. Таймеры покоя.** `IDT_TRAY_REFRESH` срабатывает каждые 5 с всегда (`src/OverlayWindow.cpp:179`), хотя тултип меняется только при пониженной частоте. Держи 5 с только пока идёт обратный отсчёт, в остальное время хватит редкой подстраховки (например 60 с). Оба таймера (этот и сторож хука, `src/InputHook.cpp:285`) переведи на `SetCoalescableTimer` с допуском. **Период сторожа хука не увеличивай.**

**3.5. Опции ImGui.** `IMGUI_DISABLE_OBSOLETE_FUNCTIONS`, `IMGUI_DISABLE_OBSOLETE_KEYIO`, `IMGUI_DISABLE_DEMO_WINDOWS`. Обязательно `PUBLIC` на цели `imgui`, как уже сделано для `IMGUI_DISABLE_DEBUG_TOOLS`. `IMGUI_DISABLE_WIN32_DEFAULT_IME_FUNCTIONS` уберёт статический импорт `IMM32.dll`, но ломает позиционирование окна IME в текстовых полях. Применяй, только если модуль реально исчезает из процесса и пользователь согласен.

**3.6. Размер кода.** Сначала собери с `/MAP` и посмотри, что занимает `.text`. Кандидаты после этого: `<iostream>` в `src/AudioManager.cpp:4` (похоже, не используется), `std::filesystem` в `Config.cpp` и `OverlayWindow.cpp` (нужны только `parent_path` и `exists`), `<future>` в `InputHook.h` ради одного `std::promise`. Делай только то, что карта покажет значимым.

## 8. Этап 4. Стоимость кадра (4.2 требует отдельного согласия пользователя)

Начинай только если S3 показал, что кадр стоит заметно (ориентир: больше ~2 мс CPU на кадр или видимое влияние на кадровое время игры).

**4.1. Меньше кадров на тик.** Каждый тик громкости вызывает `kSettleFrames = 3` кадра, потому что авторазмерное окно может перестроиться при смене ширины текста ("9%" → "10%"). Сделай ширину OSD стабильной для данного имени приложения (процент в колонке фиксированной ширины через `CalcTextSize("100%")`), тогда на обновление значения хватит одного кадра. Три кадра остаются для появления и смены имени.

**4.2. Смена модели презентации.** Сейчас: полноэкранное `WS_EX_LAYERED` окно с `LWA_COLORKEY` и blt-swapchain (`src/OverlayWindow.cpp:131,137,605-617`). Два независимых варианта:
- окно и swapchain по размеру содержимого вместо всего экрана;
- flip-модель с DirectComposition (`WS_EX_NOREDIRECTIONBITMAP`, premultiplied alpha), о которой уже написано в `CLAUDE.md` §7.

Оба меняют модель окна и прозрачности, второй ещё и внешний вид (настоящая полупрозрачность вместо color key). Это переписывание, а не настройка. **Не начинай без явного согласия пользователя**: принеси ему цифры S3 и оценку объёма.

## 9. Этап 5. Мелочи в открытом меню (низкий приоритет)

Меню открыто редко, кадры там уже событийные. Делай в последнюю очередь и только если S5 покажет проблему.

- Список шрифтов рисует все элементы каждый кадр (`src/UIManager.cpp:1230`): нужен `ImGuiListClipper`.
- `quick.Monitors()` копирует вектор со строками каждый кадр (`src/UIManager.cpp:616`), `LoadWarning()` возвращает копию строки (`:865`), `SetHdrHotkeys` вызывается каждый кадр (`:276`).
- Любое движение мыши где угодно на экране считается вводом и вызывает три полноэкранных кадра. Можно перерисовывать только когда курсор над окном ImGui или был над ним в прошлом кадре.

## 10. Чего не делать

Уже сделано, не переделывай: событийный цикл рендера, скрытие окна и освобождение устройства в простое, `thread_local` кэш WASAPI и SMTC, отложенное сохранение конфига, склейка серий тиков, LTCG и `/OPT:REF,ICF`, предкомпилированные шейдеры, отключение геймпада в бэкенде, trim рабочего набора.

Не трогай:

- `WH_KEYBOARD_LL` не заменяй на `RegisterHotKey` или Raw Input, приоритет потока хука не снижай, сторож не ослабляй. Это инвариант #1.
- Не добавляй блокировки на `g_Config` в рамках этой работы. Гонка известна и описана, её исправление является отдельной задачей.
- Не заменяй `nlohmann_json` самописным парсером. У проекта есть история с потерей конфига.
- Не переходи на статический CRT ради памяти: приватных страниц станет больше.
- Не добавляй потоки и периодические таймеры без цифр, которые это окупают.
- Не убирай SEH-обёртки и не объединяй их с функциями, владеющими C++-объектами.
- Никакого системного master volume (`IAudioEndpointVolume`): это продуктовое решение.
