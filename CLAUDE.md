# CLAUDE.md — XPG Summoner Media Volume (Smart Volume Mixer)

> Auto-loaded orientation for AI coding assistants. Keep claims grounded in `src/` at the cited `file:line` anchors. For deep detail see **ARCHITECTURE.md** at repo root.

## 1. What this is

A Windows C++20 desktop utility that fixes a **noisy hardware volume roller on the XPG Summoner keyboard**. The roller fires a flurry of `VK_VOLUME_UP` / `VK_VOLUME_DOWN` events for one physical nudge; this app installs a global low-level keyboard hook, **debounces/streams** those ticks, and applies the result to a configurable whitelist of **media applications only** (e.g. `spotify.exe`, `qobuz.exe`). It draws a transparent, click-through **DirectX 11 / Dear ImGui** OSD overlay (volume bar + "Now Playing" popup + a settings menu in a system-tray app). It also repurposes the physical **Mute key into a media play/pause toggle** and offers a configurable **"Track Info" popup**. Tech stack: **C++20, DirectX 11, Dear ImGui v1.90.4, WASAPI (per-app `ISimpleAudioVolume`), WinRT SMTC (`GlobalSystemMediaTransportControlsSessionManager`), nlohmann_json v3.11.3**.

> **Two whitelists, not one.** `mediaApps` holds the dedicated audio apps (Spotify, a player, a DAW) and is what a bare roller tick or Mute press acts on. `secondaryApps` holds the browsers, and is reachable **only while `secondaryKey` is held** (default `Pause`) - "Pause + Mute", "Pause + roller". A session that matches the browser list is never reachable from the audio group, so one Mute press can no longer pause a YouTube tab instead of Spotify (`src/AudioManager.cpp` `ProcessInGroup`/`SessionInGroup`).

> Hotkeys are **configurable**, not hardcoded. `F8` (menu) and `F9` (track info) are only the loaded **defaults** (`src/Config.h:8,13`); the hook matches `g_Config.menuKey` (`src/InputHook.cpp:119`) and `g_Config.infoKey` (`src/InputHook.cpp:132`). `infoKey == 0` disables the info popup. The menu can also be opened from the tray icon (see §3/§4).

> Important product fact: **volume control is media-apps-only by design**. Despite the README, there is **no system master volume control** (no `IAudioEndpointVolume` anywhere). "No OSD when no tracked app is playing" is **expected behavior, not a bug**. Note this is about *volume*: the app does now touch two device-wide settings deliberately — the output endpoint's default sample rate and the default output device — but only inside the quick actions in §9.

> It also carries two "mode" hotkeys that are not about volume at all — a **sample-rate toggle** (default `Alt+Q`) and a **PC↔console monitor swap** (default `Alt+S`). See §9.

## 2. Build & Run

```sh
cmake -B build -S .
cmake --build build --config Release
```

- Output: **`build/Release/SmartVolumeMixer.exe`**. A pre-built copy may already exist there (it is git-ignored along with `build/`), so a fresh clone may show a stale binary on disk.
- **The running exe locks its own binary.** Re-linking while an instance is running fails with a file-lock error — **close the running instance first** (tray icon → Exit, or kill the process), then re-build. The app also self-relaunches on crash, so make sure no zombie/restarted instance is holding the lock.
- The README documents an in-tree flow (`mkdir build && cd build && cmake ..`); the command above (`cmake -B build -S .`) is equivalent and targets the same `build/` dir — pick one convention.
- Toolchain: MSVC, C++20, no compiler extensions (`CMakeLists.txt:4-6`). The project relies on MSVC's default **`/EHsc`** exception model. This matters: under `/EHsc`, hardware faults (access violations) are **NOT** caught by C++ `catch(...)` — only by SEH `__try/__except`. The code uses SEH wrappers deliberately for this reason.
- `WIN32` GUI subsystem + `UNICODE`/`_UNICODE` defs (`CMakeLists.txt:41,62`) so `wWinMain` is the entry point.
- Dependencies are fetched at configure time via CMake `FetchContent` (network required on first configure): nlohmann_json `v3.11.3` (`CMakeLists.txt:11-16`), Dear ImGui `v1.90.4` built as a static lib with win32+dx11 backends (`CMakeLists.txt:19-39`).
- **Link inputs are split between CMake and `#pragma comment(lib,...)`.** `ole32`/`oleaut32`/`d3d11`/`windowsapp` are linked **both** in `CMakeLists.txt` **and** via pragmas (`src/AudioManager.cpp`, `src/OverlayWindow.cpp`).
- **`d3dcompiler_47.dll` is deliberately never loaded.** ImGui's DX11 backend compiles its two shaders with `D3DCompile()` at runtime; `src/ImGuiDx11Shaders.cpp` defines `D3DCompile` itself (the backend calls it without `dllimport`, so the linker binds to ours and never imports the DLL) and answers with precompiled bytecode when the source matches byte-for-byte (length + FNV-1a), falling back to a dynamically loaded real compiler otherwise. **After an ImGui upgrade, regenerate the arrays** (recipe in that file's header) — a stale table only costs the DLL load, never a wrong shader. `d3dcompiler` is therefore not in `target_link_libraries` (the backend's own `#pragma comment(lib, "d3dcompiler")` remains and is harmless: nothing references it). Likewise `IMGUI_IMPL_WIN32_DISABLE_GAMEPAD` keeps the Win32 backend from loading `xinput1_4.dll`.

## 4. Threading & COM apartment model (the most bug-prone area)

There are **four execution contexts** and **two COM apartments**. Getting this wrong is the root cause of both recently-fixed bugs.

| Code | Thread | COM apartment | Notes |
|---|---|---|---|
| `wWinMain` / `AppMain` | Main/UI | (none set here) | Lifecycle driver (`src/main.cpp:28,60`). |
| `OverlayWindow::RunLoop` + all ImGui draw + font reload + D3D device create/release | Main/UI (render) | inherited | Blocking render loop (`src/OverlayWindow.cpp` `RunLoop`). May take tens of ms (a device rebuild after idle is ~45 ms) — fine, because the hook is not on this thread. |
| `InputHook::LowLevelKeyboardProc` + `ReinstallHook` | **Hook thread** (`HookThreadMain`, `THREAD_PRIORITY_HIGHEST`) | none (no COM) | A thread that does nothing but pump the hook's messages, started by `Install()` and stopped by `Uninstall()` via `WM_QUIT`. **Must return fast**; does zero audio work. It used to share the render thread, so every frame / font rebuild delayed every key press on the system. |
| `UIManager::Render` / `RenderOSD` / `RenderMenu` | Main/UI (render) | inherited | All ImGui draw calls (`src/UIManager.cpp:110`). |
| `AudioManager::Initialize` / `Shutdown` | Main/UI | **STA** `COINIT_APARTMENTTHREADED` | `src/AudioManager.cpp:24`. Tolerates `RPC_E_CHANGED_MODE`. |
| `AudioManager::GetActiveSessions` | Main/UI (STA) | STA | Called from the Settings "Refresh" button (`src/UIManager.cpp:326`). |
| `InputHook::WorkerLoop` (debounce + all audio) | **Worker** | **MTA** `COINIT_MULTITHREADED` | Runs `ChangeVolume`/`TogglePlayPause`/`GetCurrentTrackInfo`, the quick actions, and the sample-rate timers (its `wait_until` deadline also covers `QuickActions::NextDeadline()`). |
| `QuickActions::*` (mutating) + `AudioDevices::Set*` + `DisplayControl::Set*` | **Worker (MTA)** | MTA | Reached only via the SEH wrappers `SafeSampleRateAction` / `SafeDisplayAction` / `SafeRefreshMonitors` / `SafeProcessTimers`. `EnterPcMode` **sleeps** up to `swapReturnDelayMs` (+3×1s retries) on this thread — volume events queue meanwhile, by design. |
| `AudioDevices::ListRenderDevices` (read-only) | Main/UI (STA) **and** Worker | either | Apartment-safe: local COM objects per call. The "Refresh devices" button calls it from the UI thread. |
| `QuickActions` const accessors | any | n/a | Guarded by `QuickActions::m_mutex`. Lock order is always `m_uiMutex` → `m_mutex`/`eventMutex`, never the reverse — `Notify()` is only ever called with `m_mutex` released. |
| `OnVolumeChanged` / `OnMenuToggled` / `OnTrackInfoRequested` | **Worker (MTA)** | MTA | Callbacks fire on the worker thread. `OnVolumeChanged`/`OnTrackInfoRequested` only stamp timestamps under `m_uiMutex`. **`OnMenuToggled`→`ToggleMenu` mutates `m_menuOpen` (window/UI state) from the worker** — see the race note below. |
| `OnKeyCaptured` | **Hook thread** (asymmetric!) | none | Fires **synchronously inside** `LowLevelKeyboardProc`, NOT on the worker. The lambda locks `m_uiMutex` — so it can wait out one render frame, which holds that lock — writes `g_Config`, then only `SaveDeferred()` + `RequestRedraw()`. Its `captureType` arg uses a **different** numbering than `HookEvent.type` (see below). |
| `RenderMenu` arming key capture | Main/UI (render) | inherited | `InputHook::BeginKeyCapture(type)` stores `captureType` then `isCapturingKey` (both `std::atomic`, release/acquire), so the hook thread can never see the flag with a stale type. |

**`m_menuOpen` is the most cross-thread-written UI field — and one of its reads is unlocked.** It is written from: the **worker thread** via `ToggleMenu` (F8 path, `src/UIManager.cpp:88`), the **render/UI thread** via `SetMenuOpen` (the two tray entry points — right-click → "Settings" and left double-click, `src/OverlayWindow.cpp:325,330`), and the **render thread** again via ImGui's `Begin(&m_menuOpen)` close button (`src/UIManager.cpp:184`). But `IsMenuOpen()` (`src/UIManager.h:29`) reads it **without** `m_uiMutex`, every frame, from the render loop (`src/OverlayWindow.cpp:202` → `UpdateClickability`). So invariant #6 below is **not literally true today** — `IsMenuOpen()` is a second unlocked torn-read alongside `HasActiveUI()`. Don't "fix" one by adding a lock without checking the other (and beware: `Render()` already holds `m_uiMutex` for the whole frame, and the mutex is non-recursive).

**Key-capture handshake numbering (easy to wire wrong):** the capture `captureType` enum is **0 = volume modifier, 1 = menu, 2 = info, 3 = per-app binding modifier, 4 = sample-rate key, 5 = display-swap key, 6 = browser-group hold key** (`src/UIManager.cpp` `OnKeyCaptured`, `src/InputHook.h:44-50`). This is a **different space** from `HookEvent.type` (**0 = volume, 1 = play/pause, 2 = toggle menu, 3 = track info, 4 = per-app mute, 5 = sample-rate action, 6 = display-swap action, 7 = rescan monitors**, `src/InputHook.h:12-19`). They overlap numerically but mean different things — do not cross the constants. Only capture types **0, 3 and 6** accept a bare Ctrl/Shift/Alt press (all three bind a *held* key); every other type skips modifier-only keys (`src/InputHook.cpp` capture branch).

**The cross-apartment rule that was violated and fixed:** a COM interface pointer created in the STA (main thread) must **never** be dereferenced from the MTA worker thread — that is undefined behavior. The original code shared `AudioManager::m_pEnumerator` (STA) into `ChangeVolume` (MTA worker) → intermittent fault (crash) or silent failure (no OSD). Now `AudioManager::GetSessionEnumerator` builds the whole chain in the caller's own apartment and keeps it in a **`thread_local` cache** — which is what preserves the rule: a thread can only ever see the pointers it built itself, so an STA pointer is structurally unreachable from the MTA worker. `m_pEnumerator` is kept only as a startup capability check in `Initialize`.

The cache holds the `IMMDeviceEnumerator` + `IAudioSessionManager2` for 1.5 s (the *session enumerator* is still taken fresh on every call, so a newly-playing app is picked up as before), and is dropped on any failure, on a TTL expiry, and whenever `AudioManager::InvalidateDeviceCache()` is called — which `AudioDevices::SetDefaultRenderDevice` does after a successful endpoint switch. **A thread must call `AudioManager::ReleaseThreadCache()` before its `CoUninitialize()`** (`AudioManager::Shutdown` and the end of `WorkerLoop` both do); a `thread_local` destructor would run after COM is already gone.

## 5. Critical invariants

1. **The keyboard hook MUST stay installed.** `VK_VOLUME_MUTE` is swallowed (`LowLevelKeyboardProc` returns 1) and repurposed to play/pause. If the hook dies, Mute reverts to the OS default and **mutes the entire system**. The whole crash→`RestartSelf` design exists to re-establish the hook (`src/main.cpp:8-11`, `src/InputHook.cpp:7-11`). A 5s watchdog also reinstalls it — a thread timer on the hook thread itself (`InputHook::HookThreadMain` → `ReinstallHook`); an LL hook can only be (re)installed from the thread that pumps it.
2. **A fault on the worker thread must never escape.** Under `/EHsc`, hardware faults bypass C++ `catch(...)`. Every worker audio call goes through SEH wrappers `SafeChangeVolume`/`SafeTogglePlayPause`/`SafeGetTrackInfo` (`src/InputHook.cpp:15-44`), and the process-wide `SetUnhandledExceptionFilter(GlobalCrashHandler)` (`src/main.cpp:62`) catches anything that still escapes (the main-thread `__try` cannot see worker faults).
3. **All WASAPI/WinRT calls run on the MTA worker, never the STA main thread**, and the `thread_local`-cache rule above must hold — including releasing that cache before `CoUninitialize` (`src/AudioManager.cpp`).
4. **Startup order is mandatory** (`src/main.cpp:29-51`): `Config.Load` → `AudioManager.Initialize` → `UIManager.Initialize` → `InputHook.Install` → `OverlayWindow.Create` → `RunLoop`. Teardown is `OverlayWindow.Destroy` → `InputHook.Uninstall` → `AudioManager.Shutdown` (`src/main.cpp:53-55`).
5. **`g_Config` is a mutable global shared across threads with NO locking** (`src/Config.cpp:11`). Load runs once on the main thread before any other thread exists (`src/main.cpp:29`), so initial population is race-free; subsequent concurrent reads/writes are technically racy (see §7).
6. **`m_uiMutex` must be held for all UI-state reads/writes** in `UIManager`, and `Render()` holds it for the whole frame — so `RenderOSD`/`RenderMenu` must NOT re-lock (`std::mutex` is non-recursive) (`src/UIManager.h:49`, `src/UIManager.cpp:110`).
7. **SEH `__try/__except` functions must not own C++ locals with destructors** under `/EHsc` (MSVC error C2712). That is why `SafeGetTrackInfo` delegates the `std::string` work to `GetTrackInfoInner`. (A wrapper may freely *call* a function that owns such locals — that is why `SafeSampleRateAction` and friends need no inner helper.)
8. **DDC/CI and `ChangeDisplaySettingsEx` must never run on the UI thread.** A DDC round-trip takes 50–200 ms+ per monitor, and the UI thread is what draws the OSD and answers the tray icon. (It used to be worse: the LL keyboard hook lived on that thread too, and Windows silently unhooks a hook past `LowLevelHooksTimeout`. The hook has its own thread now, but the rule stands.) The settings menu therefore *enqueues* worker events (`EnqueueWorkerAction` in `src/UIManager.cpp`, event types 5/6/7) instead of calling these APIs directly. Same rule for the tray menu (`src/OverlayWindow.cpp` `WM_TRAYICON`).
9. **A lowered sample rate must always have a way back.** It is persisted (`srActive`/`srRevertAtUnix`/`srSavedHz`/`srActiveDeviceId`) so a restart re-arms the deadline (`QuickActions::LoadPersistedState`, called from `AppMain` right after `Config.Load`), the worker restores it on shutdown before `CoUninitialize` (`srRevertOnExit`), and a failed restore re-arms a 5-minute retry rather than clearing the state.
10. **The render loop only draws when what is on screen changes.** It redraws `kSettleFrames` (3) frames when `UIManager::VisibleMask()` changes (a popup appears or expires, the menu opens/closes) or when the `OverlayWindow::RequestRedraw()` count moves, then sleeps until the next popup expiry (`MsUntilNextExpiry`); the last presented frame simply stays up. So *anything* that changes what is shown from another thread must call `RequestRedraw()` — every `UIManager::Show*`/`ToggleMenu`/`SetMenuOpen` setter and the key-capture callback do. The request is a counter, so a call made before the window exists is still picked up. With the menu open it also redraws on any window message (input), every frame while a text field is focused, and once a second. **Anything animated would need its own wake** — nothing in the UI animates today. The 5 s tray-refresh `WM_TIMER` (`IDT_TRAY_REFRESH`) is the backstop wake.
11. **The overlay window is hidden while idle, and has no D3D device after 30 s of that.** A visible fullscreen layered TOPMOST window is composited by DWM every frame regardless of content, and can hold fullscreen apps off the independent-flip path. `SetOverlayVisible` shows it with `SW_SHOWNOACTIVATE` (never steal focus) on the first frame with content and hides it after the trailing clearing frame — so code must not assume the window is visible, and must not rely on `SW_SHOWDEFAULT` at startup for anything. `IdleCleanup` then releases the D3D device, ImGui's DX11 backend and the swapchain, and trims the working set; `RenderFrame` → `RecreateDevice` → `RebuildFonts` brings everything back (~45 ms, measured). Code on the render thread must not assume a device or swapchain exists, and must never call `ImGui_ImplDX11_CreateDeviceObjects` directly: the font atlas keeps no input data after upload, so only `RebuildFonts` (which re-adds the fonts) may build it.
12. **Narrow string literals stay ASCII.** The tray tooltip widens bytes one-by-one (`std::wstring(line.begin(), line.end())`), so a UTF-8 em dash there would corrupt it. ImGui strings would survive, but the codebase keeps one rule.

## 6. Recent changes / fixes

Shared root cause of both bugs: **unsafe cross-thread COM + an unguarded worker thread**.

**Bug 1 — rare crash, after which the Mute key muted the WHOLE system.** The worker thread ran COM/WinRT with no exception guard; under `/EHsc` a hardware fault (access violation on a stale audio session) was not caught by `catch(...)`, and the `wWinMain` `__try/__except` only guarded the main thread. A worker fault killed the process — bypassing auto-restart — leaving the hook dead, so swallowed Mute reverted to OS default and muted everything.
- Fix `src/main.cpp`: added `SetUnhandledExceptionFilter(GlobalCrashHandler)` + `RestartSelf()` to relaunch on a fault on **any** thread (`src/main.cpp:23,62`).
- Fix `src/InputHook.cpp`: wrapped the three worker audio calls in standalone SEH helpers `SafeChangeVolume`/`SafeTogglePlayPause`/`SafeGetTrackInfo`; `SafeGetTrackInfo` delegates to `GetTrackInfoInner` to avoid C2712 (`src/InputHook.cpp:15-44`).

**Bug 2 — the volume OSD did not appear when scrolling the wheel.** The OSD shows only when `ChangeVolume` returns true. The shared `m_pEnumerator` was created STA (main thread) but used from the MTA worker in `ChangeVolume` — cross-apartment UB that intermittently faulted or silently failed (→ `ChangeVolume` false → no OSD).
- Fix `src/AudioManager.cpp`: `GetSessionEnumerator` now creates a **local `IMMDeviceEnumerator` per call** in the caller's apartment (self-healing + apartment-safe); `m_pEnumerator` retained only as a startup capability check (`src/AudioManager.cpp:38-49`).

**Product decision (confirmed with user): media-apps-only.** Do NOT add a system master volume (`IAudioEndpointVolume`) fallback. Therefore "no OSD when no tracked app is active" is **expected**, not a bug.

Verification status: all translation units compiled clean (no warnings, no C2712); Release linked and relaunched (the only link failure was the running instance locking the `.exe`). The rare crash (Bug 1) could not be reproduced synthetically — it is infrequent by nature.

## 7. Known issues / gotchas / footguns

- **README overpromises.** `README.md:26` and `:42` claim system master volume via `IAudioEndpointVolume`; **no such code exists** — per-app `ISimpleAudioVolume` only (`src/AudioManager.cpp:91`). Do NOT assume master-volume control exists. `README.md:41` also says "microsecond window" for debounce — the code uses **milliseconds** (`volDebounceWindowMs=200`).
- **Debounce eats isolated single ticks at the default threshold (2).** With `volDebounceThreshold=2`, a single clean tick starts a debounce window but does not fire until a second tick arrives within the window; an isolated tick is swallowed (`src/InputHook.cpp:244-289`). Set threshold to 1 for "no debounce" (the `<=1` fast path fires immediately, `src/InputHook.cpp:268`).
- **`VisibleMask()` / `MsUntilNextExpiry()` / `HasActiveUI()` read the `m_*ShowTime` stamps (64-bit) without locking `m_uiMutex`** while another thread writes them under the lock — a torn-read data race; in practice only gates a frame early/late, and the `RequestRedraw()` counter that accompanies every write is what actually triggers the redraw (`src/UIManager.cpp`).
- **`g_Config` data race.** No mutex/atomic; the UI thread writes fields and calls `Save()` on essentially every edit while the hook callback, worker, and audio paths read concurrently. `mediaApps` (a `std::vector` that can reallocate) is the worst foot-gun (`src/Config.cpp`, consumers `AudioManager.cpp:115,188`).
- **`OnKeyCaptured` no longer does disk I/O inside the LL keyboard hook** — it calls `g_Config.SaveDeferred()` (a flag) plus `RequestRedraw()`, and the render loop performs the write. Keep it that way: slow work in a LL hook risks Windows silently removing the hook past `LowLevelHooksTimeout` (`src/UIManager.cpp`, `src/InputHook.cpp:115`).
- **A settings edit is in memory before it is on disk.** `SaveDeferred()` stamps the first unsaved edit; the render loop writes once that is ≥400 ms old (`kSaveCoalesceMs` in `src/Config.cpp`), so a slider drag reaches the disk a few times a second instead of once per frame (it used to be per frame while the menu was open), and teardown in `AppMain` forces a final `FlushPendingSave(true)`. A hard kill in that window loses the last edit; anything that must survive a crash (the quick actions' persisted runtime state) still calls `Save()` directly.
- **A corrupt `config.json` used to silently wipe every setting, and an empty `mediaApps` makes the app look completely dead.** This actually happened and it is worth understanding, because none of the three symptoms points at the config: the roller did nothing, the Mute key did nothing, and `Alt+S` did nothing. The hook was alive the whole time — that is *why* nothing happened at all. An empty whitelist makes `ChangeVolume`/`TogglePlayPause` no-op while the hook still returns 1 and swallows the key, so the keys neither work nor fall through to Windows. (If the hook were genuinely dead you would see the opposite: the roller would move the *system* volume and Mute would mute everything.) Three defects chained, all now fixed in `src/Config.cpp`:
  - **Two disagreeing default sets.** The first-run branch seeded 21 apps; the parse path used `j.value("mediaApps", std::vector<std::string>{})` — an **empty** fallback. Any config missing that one key silently disabled the whole app. There is now a single `DefaultMediaApps()`, and a *missing* key gets it while a *present* empty array is respected (the user may have meant it) and called out in the menu.
  - **A failed parse was silent and then overwritten.** `file >> j` parses the entire document before assigning anything, so a throw left every field at its struct default; `catch (...) {}` swallowed it, and the next `Save()` — a settings edit, or `QuickActions` persisting swap state from the worker — wrote those defaults over the real config. `Load()` now parses into a temporary and commits only on success, tries `config.json.bak` before defaults, and renames anything unparseable to `config.json.corrupt-<unix>` instead of leaving it to be clobbered.
  - **`Save()` truncated the live file.** `std::ofstream(path)` zeroes config.json before the first byte of new content lands. In an app built around a crash→relaunch net that also force-kills `SystemSettings.exe` and drives display/DDC drivers, dying in that window is realistic — and a truncated file then failed to parse on the next launch, feeding the two defects above. `Save()` now writes `config.json.tmp`, copies the current file to `config.json.bak`, and commits with `MoveFileExA(..., MOVEFILE_REPLACE_EXISTING | MOVEFILE_WRITE_THROUGH)`. `Load()` also refreshes the `.bak` as soon as the live file proves it parses, so a fresh instance is never without a recovery source.
  - The settings menu now shows a recovery banner when `AppConfig::LoadWarning()` is non-empty, and the Applications tab warns on an empty whitelist with a "Restore default app list" button — an empty list must never again present itself as a broken app.
- **`swapAudioConsole` defaults to `"Pebble"`, not `"K7"`.** The old default regenerated a config that sends PC audio into the K7's USB input while the K7 is listening to LINE — i.e. silence on every swap. Defaults on this machine should regenerate into a *working* state; see the wiring note below.
- **`fontSmall`/`fontMono` no longer exist.** They were built into the atlas on every launch and never drawn with. The "Small Size" slider in the Customization tab therefore still writes `fontSizeSmall` to the config but changes nothing on screen — as was already true before they were removed.
- **Two matching semantics:** volume uses exact process-basename equality (`NameMatchesExact`); SMTC uses looser AUMID exact/substring match (`AumidMatches`). An app can match for media keys but not for volume, or vice-versa. Both go through `ProcessInGroup`/`SessionInGroup`, where **the browser list wins**: a session matching `secondaryApps` is excluded from the audio group outright, so a loose AUMID substring can never leak a browser back into the bare-Mute path. Measured AUMIDs on this machine: Edge reports `MSEdge`, Spotify reports `Spotify.exe`, Telegram reports `Telegram.TelegramDesktop`.
- **The browser group's hold key cannot rely on `GetAsyncKeyState` alone.** `Pause`/`Break` reports its key-up the instant it is pressed on most keyboards, so "is it held" is unanswerable at the moment the roller tick arrives. The hook therefore stamps every press of `secondaryKey` (passing the key through - it still belongs to the focused app) and treats it as held for `secondaryHoldMs` (default 1500), refreshed by every tick it routes so a long roll does not fall back to the audio apps halfway. Verified by injected input: bare roller -> Spotify only; Pause held + roller -> Edge only; Pause tapped then roller inside the window -> Edge only; after the window -> Spotify again. Same four results for the Mute key.
- **A per-app binding shadows the browser group** if both use the same modifier: `LowLevelKeyboardProc` checks `appBindings` first and returns early, so binding `Pause` to one app in the Per-App Bindings tab takes `Pause + roller` away from the browser list.
- **The debounce accumulator does not separate the groups.** `accumulatedTicks` is one counter, and when it fires it applies every accumulated tick to whichever group the *firing* event carries. So one bare tick followed within `volDebounceWindowMs` by a Pause-held tick sends both to the browser. Same pre-existing quirk as `bindingIndex` (a per-app binding picked up mid-window), harmless at a 200 ms window, and the price of one shared state machine.
- **No single-instance guard / no restart-loop guard.** Repeated crashes can spawn multiple instances (`src/main.cpp` notImplemented).
- **`RestartSelf` uses ANSI APIs** (`GetModuleFileNameA`/`ShellExecuteA`) in a UNICODE build; non-ANSI exe paths can fail to relaunch (`src/main.cpp:12`). `config.json` path is likewise ANSI.
- **Device loss is recovered, and no longer ends the app.** `RecreateDevice` shuts ImGui's DX11 backend down and re-`Init`s it around the new device (it used to only recreate the backend's objects — on the old, dead device), and a device that cannot be recreated yet is retried every 2 s instead of breaking out of `RunLoop` (which used to exit the process, and with it drop the hook). Primary-monitor-only, no DPI awareness.
- **The ~14 MB "shared" GPU allocation is the driver's, not ours.** Presenting a blt-model swapchain into a `WS_EX_LAYERED` window makes the AMD driver cache a window-sized system-memory staging surface. It survives releasing the swapchain, shrinking the window and `IDXGIDevice3::Trim()` (all three measured); only releasing the device frees it — which is one reason `IdleCleanup` releases the whole device. A DirectComposition / flip-model overlay (`WS_EX_NOREDIRECTIONBITMAP`, premultiplied alpha) would avoid it entirely, at the cost of rewriting the window/transparency model.
- **The quick-action hotkeys are swallowed system-wide.** `Alt+Q` / `Alt+S` return 1 from the hook when their modifier gate passes, so those combos stop reaching every other app. Both are rebindable (Audio Quality / PC-Console tabs); `srKey == 0` / `swapKey == 0` disables one entirely. Like the pre-existing menu/info gates, `ModifiersHeld` only checks that *required* modifiers are down — extra ones are ignored, so `Ctrl+Alt+Q` fires too.
- **`IPolicyConfig` is undocumented.** `src/PolicyConfig.h` is a hand-written vtable; a Windows change could break `SetDeviceFormat`/`SetDefaultEndpoint` with no compile-time warning. The sample-rate path falls back to a property-store write, but the default-device switch has no fallback.
- **Verify a sample-rate change against the LIVE engine, not the stored value — and NOT against the Windows Sound UI.** `PKEY_AudioEngine_DeviceFormat` (and its registry copy) is the *stored* default; it changes even when nothing reaches the running audio engine. The real check is `IAudioClient::GetMixFormat` on the endpoint. **Measured on this machine:** `IPolicyConfig::SetDeviceFormat` genuinely applies live (stored *and* mix format both move, 384000↔192000, in **both** STA and MTA apartments — apartment is not a factor), and the change persists indefinitely (nothing reverts it). The `Alt+Q` path works end to end. **The Windows Settings app lies about it:** `SystemSettings.exe` stays resident in the background and serves a cached Format value, so `ms-settings:sound-defaultoutputproperties` can show `384000 Hz` while the endpoint is really at `192000`. Confirmed by screenshot: killing `SystemSettings.exe` and reopening the page shows the correct `192000 Hz`. The legacy `mmsys.cpl` Advanced tab caches the same way. **Never** use either UI to judge whether this feature worked — use `GetMixFormat`.
  - `AudioDevices::SetSampleRate`'s `outAppliedLive` out-param reports which path was taken (`true` = `SetDeviceFormat`; `false` = only the property-store fallback, which updates the stored default but has not been observed to reach an already-running engine); callers append `"(stored only - <reason>)"` and flag the notice as an error in that case.
  - Since users have no way to tell "really 192kHz, UI is lying" from "actually still 384kHz" by looking at Settings, `QuickActions::LowerRate`/`RestoreRate` call `RefreshSettingsAppCache()` (`src/QuickActions.cpp`) after every `appliedLive == true` change: it enumerates processes via `CreateToolhelp32Snapshot`/`Process32NextW` and `TerminateProcess`es any `SystemSettings.exe`. There is no API to invalidate just its cache — the whole host process has to go, and Windows relaunches it fresh (no data loss; it is a settings UI, not a document editor) the next time Settings is opened. Verified end-to-end: opened Settings (showed the stale 192kHz correctly since freshly launched), triggered the restore via `Alt+Q`, confirmed the *specific* `SystemSettings.exe` PID was gone within ~2s, reopened Settings and it showed the correct `384000 Hz` with zero manual intervention. Gated by `srRefreshSettingsApp` (default **on**) since it force-closes a window that might be open for something unrelated.
- **This machine has AMD GPUs (Radeon RX 9070 XT + an APU iGPU), not NVIDIA** — `Win32_VideoController` is the source of truth; an earlier pass at this doc got this wrong by pattern-matching "dual monitor + `ChangeDisplaySettingsEx` bug" to NVIDIA without checking.
- **DDC/CI reads succeeding while writes are silently ignored does not mean input switching is impossible — it means the standard channel is the wrong channel.** Verified on this machine's LG UltraGear 27GS85Q-B: `GetVCPFeatureAndVCPFeatureReply(0x60)` returns the current input correctly (`0x0F` = DisplayPort), but `SetVCPFeature(0x60, 0x12)` returns `TRUE` — the DDC/CI transaction completes — while the monitor never switches, and a read-back confirms the value is unchanged; the monitor acknowledges the write and discards it. `DisplayControl::DoSetInput` sleeps ~400 ms and reads the value back, failing the call with the read-back value in the error instead of trusting the return code — **but this read-back is not reliable evidence either way once the LG side-channel below is in play**: switching *away* from DisplayPort via the standard channel consistently fails this check, while switching *back to* DisplayPort via the standard channel has been observed to both fail the check and, once, pass it while a real user confirmed the physical switch — i.e. this specific panel's standard-channel behavior is asymmetric and not fully understood, only worked around (see below). This step is otherwise independent: primary-display and audio switching still run and succeed when it fails.
- **A real, working fix for "ACK'd but ignored" LG input-switch writes exists: an undocumented per-model service side-channel, reachable only through the GPU vendor's raw I2C API.** LG's standard DDC/CI "Set VCP Feature" packet is `[0x6E, 0x51, 0x84, 0x03, VCP, valHi, valLo, checksum]` (dest addr, **source addr**, length, opcode, feature code, 2-byte value, XOR checksum of every preceding byte including the dest addr); some LG models simply ignore VCP `0x60` (input select) sent this way. The undocumented fix, reverse-engineered by the ddcutil/community (`github.com/rockowitz/ddcutil/wiki/Switching-input-source-on-LG-monitors`, `github.com/amildahl/amdddc-windows`), is the *same* packet shape with **source addr `0x50` instead of `0x51`** and **feature code `0xF4` instead of `0x60`** — everything else, including the checksum formula, is identical. Values are model-specific; **verified empirically on this LG UltraGear 27GS85Q-B via the real `Alt+S` hotkey: `0xD0` = DisplayPort, `0x91` = HDMI-2** (the values documented for other LG models — 32GP83B, DualUp — turned out to carry over). The standard Windows `dxva2.dll` DDC/CI API has **no parameter to override the source-addr byte**, so this channel is unreachable through it at any privilege level; it requires a GPU vendor's own raw-I2C API — on this AMD machine, **ADL** (`ADL_Display_DDCBlockAccess_Get`, loaded dynamically from `atiadlxx.dll`; the minimal header subset lives in `src/AmdAdl.h`, mirroring `github.com/GPUOpen-LibrariesAndSDKs/display-library`, MIT). `src/AmdDdcSideChannel.cpp` implements this and `QuickActions.cpp` calls it **only as a fallback** when the standard path's read-back verification reports failure, gated by `swapUseAmdSideChannel` (default on).
  - **The two "which monitor is this" match strings are for unrelated APIs and are NOT interchangeable.** `swapMonitorMatch` matches the PnP id substring the standard GDI/dxva2 path uses (`"GSM"` for this LG); ADL enumerates the *same physical monitor* under its EDID-derived friendly name instead (`"LG ULTRAGEAR"` on this unit) — hence the separate `swapMonitorMatchAmd` field (default `"ULTRAGEAR"`). Getting this wrong silently no-ops the fallback with a "no ADL display matching" error, which was in fact hit once during development and looked like the fallback wasn't engaging at all.
  - **The same "no ADL display matching" error also appears when `System32\atiadlxx.dll` belongs to a different AMD driver package than the one the GPUs are bound to.** Hit on 2026-10-30: the adapters ran `32.0.21030.2001` (`u0420529.inf`) while System32 held ADL `7.26.10.1609` from a newer staged package (`u0204192.inf`, `32.0.31044.16`). The mismatched ADL loads, creates its context and lists all 10 adapters fine — but reports **zero displays on every one** (and `ADL2_Adapter_Active_Get` = 0 everywhere), so no match string can ever work. **The general rule: an ADL build only sees displays on GPUs bound to its own driver package.** Hit a second time on 2026-11-01, after a driver update left the two GPUs on *different* packages (iGPU `u0205305` / `32.0.21045.16010`, ADL `7.25.10.1590`; RX 9070 XT `u0205306` / `32.0.32015.7029`, ADL `7.26.20.1616`): the iGPU's ADL saw only `VG220Q`, the dGPU's saw both monitors, so picking "the first bound package" was not enough. `AmdDdcSideChannel::SetInput` therefore tries **every** candidate (`AdlCandidates()`: the `atiadlxx.dll` from each present display adapter's bound DriverStore folder, found via SetupAPI → `DIREG_DRV` key → `UserModeDriverName`, then System32) and uses the first one whose `FindDisplay` matches. Loading and unloading several ADL copies in a row in one process was measured to work. When no candidate matches, the error lists every name any ADL saw, or says no ADL saw a connected display at all.
  - **This side channel does not confirm success** (the community's own tooling needs a `--noverify`-equivalent for it), so `AmdDdcSideChannel::SetInput` reports only whether `ADL_Display_DDCBlockAccess_Get` itself succeeded — never whether the monitor reacted. Confirming this genuinely works required a person watching the physical screen, not just automated checks.
- **The primary-display swap must use `SetDisplayConfig`, NOT the legacy `ChangeDisplaySettingsEx` batch.** The widely-copied legacy recipe (stage each adapter's `dmPosition` with `CDS_UPDATEREGISTRY|CDS_NORESET`, target carries `CDS_SET_PRIMARY`, commit with a null-device call) was **measured to fail on this machine**: whichever adapter is staged **second** returns `DISP_CHANGE_FAILED` — regardless of processing order and regardless of which one carries `CDS_SET_PRIMARY` — while the final commit still reports `DISP_CHANGE_SUCCESSFUL` and nothing moves. Root cause: a staged batch necessarily passes through an invalid intermediate state (after the first call either no display is at `(0,0)` or two are), and this driver validates eagerly instead of deferring to the commit as `CDS_NORESET` documents. Confirmed **not** to help: reordering the target first; passing full `dmFields` instead of `DM_POSITION` alone (makes *both* calls fail); splitting into two separate immediate transactions. `SetPrimaryMonitor` now submits the whole `QueryDisplayConfig` path/mode array in one `SetDisplayConfig(SDC_APPLY|SDC_USE_SUPPLIED_DISPLAY_CONFIG|SDC_SAVE_TO_DATABASE|SDC_ALLOW_CHANGES)` call, shifting every source mode so the target lands at `(0,0)` — verified working in both directions, both standalone and via the real `Alt+S` hotkey. It still read-back-verifies the resulting position rather than trusting the return code.
- **A "swap" step that targets the device/state already in effect is a no-op, not a bug.** `EnterConsoleMode`/`EnterPcMode` report `"Output already <name>"` in that case so it cannot be mistaken for a silent failure. `SetDefaultEndpoint` itself is verified working. **This machine's wiring:** PC → K7 over **USB**, PS5 → K7 over **LINE**; the K7's input selector is a front-panel knob with no software control, so the only automatable half is *which Windows endpoint gets PC audio*. Configured accordingly: `swapAudioConsole = "Pebble"` (in console mode the K7 is listening to LINE, so PC audio over USB would be inaudible — it moves to the Pebble V3) and `swapAudioPc = "K7"`. Verified switching both ways.
- **Making a display primary does NOT move existing windows** — Windows only relocates *new* ones. `DisplayControl::MoveWindowsToMonitor` (gated by `swapMoveWindows`, default on) does it explicitly, scaling each window proportionally into the target's work area. Two non-obvious details, both learned by measurement: a **maximized** window ignores a changed `WINDOWPLACEMENT::rcNormalPosition` and stays maximized on its current monitor, so it must be set to `SW_SHOWNORMAL` (which lands it on the target) and then re-maximized with `ShowWindow(SW_SHOWMAXIMIZED)`; and the filter must skip owned windows, `WS_EX_TOOLWINDOW`, untitled windows, DWM-**cloaked** UWP hosts, the shell classes (`Shell_TrayWnd`/`Progman`/`WorkerW`/…) and this app's own `SmartMixerClass` overlay.
- **A window's placement must be captured *before* the primary-display swap, not during the move — capturing it after silently corrupts the coordinates.** The desktop's coordinate origin shifts wherever the new primary is; `MoveWindowsToMonitor` used to call `GetWindowPlacement` *inside* itself, which by construction only ever runs *after* `SetPrimaryMonitor` — so the "original" position it recorded for `RestoreWindows` was already in the *new* (console-mode) coordinate space, not the space the desktop returns to once PC mode flips primary back. Confirmed by measurement: every window's restored position was off by a small, inconsistent amount (not the full monitor-width offset naively expected, because `SetWindowPlacement` clamps a badly out-of-range rect back onto some visible monitor first) — since it silently landed *somewhere plausible*, this reads as "window management is a bit off" rather than an obvious crash, and is easy to miss without literally comparing pixel rects before/after. Fixed by splitting into `DisplayControl::SnapshotWindows()` (called once, before `SetPrimaryMonitor`, in `EnterConsoleMode`) and `MoveWindowsToMonitor(snapshot, target)` (called after, using the snapshot's pre-swap placement as what gets recorded, while still reading each window's *current* position fresh for the scaling math, which is unaffected by the origin shift since source and destination are both queried in the same post-shift frame). Verified via direct `GetWindowRect`/`EnumWindows` measurement across a real `Alt+S` PC→console→PC round trip: every tracked window landed back at its exact pre-swap pixel rect.
- **Chromium/Electron apps can silently fight a `SetWindowPlacement` restore.** Observed on this machine: the Claude desktop client and Discord (both Chromium-based) sometimes repositioned themselves a moment *after* `RestoreWindows` placed them back on the original monitor, apparently reacting to the `WM_DISPLAYCHANGE` the primary swap fires and re-homing onto whatever they consider "current." `RestoreWindows` mitigates this with a second identical `SetWindowPlacement` pass ~200ms after the first, giving our placement the last word — cheap since this only ever runs on the MTA worker thread, never the LL hook thread.
- **`config.json` now holds runtime state** (`srActive`, `srRevertAtUnix`, `swapConsoleMode`, `swapSavedAudioId`), written from the worker thread. `Save()` is file-mutex-serialised, but the underlying `g_Config` field race (below) is unchanged.
- **Stray repo files (not in the build):** `smtc_test.cpp`, `test.cpp` (garbage/UTF-16 stub), `smtc_test.exe/.obj`, `debug_hook.log` (×2, contain old keystroke traces — nothing in current `src/` writes them), `imgui.ini`, and ~28 MB of unextracted font ZIPs in `fonts/`. None are referenced by `CMakeLists.txt`.

## 8. Conventions

- **Singletons via `Get()`** (Meyers): `AudioManager::Get()`, `InputHook::Get()`, `UIManager::Get()`, `OverlayWindow::Get()`, plus the global `g_Config`.
- **COM lifetime via `Microsoft::WRL::ComPtr`** (`wrl/client.h`); release order matters in DX11 cleanup.
- **SEH wrapper pattern:** any worker-thread call into COM/WinRT/audio goes through a standalone `__try/__except` helper that owns no C++ destructible locals; the C++ work lives in a separate inner function (see `SafeGetTrackInfo`/`GetTrackInfoInner`).
- **No C++ exceptions across the LL hook**, and the hook does no audio work — it only enqueues events and returns fast.
- **Comments and docs are English** (match the existing style).
- Cross-thread UI state changes go through `UIManager` setters that take `m_uiMutex`; worker callbacks must not call ImGui directly.

## 9. Quick actions: sample-rate toggle & PC↔console swap

Both live in `src/QuickActions.cpp`, are triggered by a hotkey (LL hook → worker event), and report via a top-centre notice OSD (`UIManager::ShowNotice`, 5 s) plus the tray tooltip.

**Sample rate (`Alt+Q`, `HookEvent.type == 5`, arg 0=toggle / 1=restore / 2=lower).** Rewrites *only* `nSamplesPerSec` (plus the derived `nBlockAlign`/`nAvgBytesPerSec`) of the endpoint's stored default format, so the DAC never receives a format it did not already advertise. Two paths, in order: `IPolicyConfig::SetDeviceFormat` (what the Sound control panel's Advanced tab calls — applies live), then a direct `PKEY_AudioEngine_DeviceFormat` + `PKEY_AudioEngine_OEMFormat` property-store write as fallback. Verified hardware baseline on this machine: **FiiO K7 = 384000 Hz / 32-bit / 2ch**, `dwChannelMask` 3, `KSDATAFORMAT_SUBTYPE_PCM`.
- Reading the rate goes through `IPropertyStore` (`STGM_READ`) — **not** the registry. The registry copy at `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\MMDevices\Audio\Render\{id}\Properties` prefixes the blob with 8 bytes (`41 00 00 00 01 00 00 00`) before the `WAVEFORMATEXTENSIBLE`; `GetValue` hands back the payload only. Useful for out-of-band verification, misleading if you parse it at offset 0.
- `PKEY_Device_FriendlyName` (`{a45c254e…},14`) is **synthesised**, not stored — it is absent from the registry key above. `ReadDeviceName` falls back to `{b3f8fa53…},6` then `{a45c254e…},2`.
- Timers ride the worker's existing `wait_until`; there is **no extra thread**. Reminder cadence is `srReminderMinutes` (0 = off), revert is `srAutoRevertMinutes` (0 = never).
- Pressing the hotkey when the device is *already* at `srLowHz` (e.g. changed externally) restores `srHighHz` instead of no-oping.

**Console swap (`Alt+S`, `HookEvent.type == 6`, arg 0=toggle / 1=PC / 2=console).** Order matters and is deliberate:
- → console: remember the current default output, **set primary first** (while the PC still owns the panel), *then* flip the monitor input, then switch the default output. Doing the input flip first would leave windows on a screen already showing the console.
- → PC: flip the input back **first**, then wait `swapReturnDelayMs` (+ up to 3×1 s retries) for the DisplayPort link to re-negotiate before making the monitor primary again, then restore audio.
- Monitor targeting is a case-insensitive substring of the PnP device id / description / GDI name (`DisplayControl::Matches`). Verified on this machine: LG = `MONITOR\GSM5C97\…` (hence the `"GSM"` default), second monitor = `ACR06D8` (an **Acer VG220Q**, not an Asus). `swapPrimaryConsoleMatch` empty = "first display that is not the swap monitor", which is why the second monitor needs no identifier.
- VCP `0x60` values are configurable because monitors deviate from MCCS. The settings table shows what the monitor *currently* reports plus "Save as PC/console input" buttons — that is the intended discovery workflow (select the input on the monitor, rescan, save).
- **This LG panel ignores the standard VCP `0x60` write for switching away from DisplayPort**, confirmed by read-back. `QuickActions` falls back to `AmdDdcSideChannel::SetInput` (`swapUseAmdSideChannel`, on by default) when that happens — the undocumented LG service side-channel, reached via AMD ADL since the standard `dxva2.dll` API cannot express it. Verified via the real hotkey: `0xD0`→DisplayPort, `0x91`→HDMI-2 (`swapInputPcAmd`/`swapInputConsoleAmd`). Targets the monitor by its ADL display name (`swapMonitorMatchAmd`, default `"ULTRAGEAR"`) — **not** `swapMonitorMatch` (that's the PnP-id substring for the unrelated standard path). See CLAUDE.md §7 for the full packet format and how this was found.
- A primary swap fires `WM_DISPLAYCHANGE`; `OverlayWindow::OnDisplayChanged` re-fits the overlay to the new primary and calls `ResizeBuffers`. Without it the OSD would sit at stale coordinates.
- **Not implemented on purpose:** detaching the LG from the desktop, and any control of the K7's own input selector (that is a physical knob).
